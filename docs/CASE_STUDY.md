## 1. 改了科目或資料，舊核准還能用嗎？

**問題。** 核准不是對一個編號永久同意，而是針對當時的來源、金額、政策與版本。只改設定中的科目名稱，或讓舊案件一律套最新科目，會改變過去處理的意義。

**系統的處理原則。** 補件產生新憑證版本、重新確認及覆核；科目修訂保留前版、獨立決策與生效條件。已過帳資料透過受控更正接到新結果，不直接改掉原帳。後續結算須辨認目前有效的認列，同時保留當時實際使用的科目依據。

**為什麼跨模組？** 原生命週期修復紀錄曾指出：軟關帳使已核准更正無法執行，待更正又阻擋硬關帳，而當時的重開只接受硬關帳；單一命令都在「正確拒絕」，合在一起卻無路可走。另一問題是替代分錄與原認列的關係，會同時影響配對、結算及追溯。只修畫面或借貸平衡不足以解決。

| 要檢查的情況 | 必須保留的結果 |
| --- | --- |
| 未過帳資料補件 | 保留原件，新版重新取得必要確認與核准。 |
| 科目修訂後查舊帳 | 能辨認原使用版本，不以新設定覆寫歷史。 |
| 更正後接續收付款 | 查到適用的目前認列，不重複消耗銀行證據。 |
| 期間阻擋更正 | 經受控重開與重驗處理，不直接放寬關帳限制。 |

**取捨。** 接受版本、審批及使用當下重驗的成本，換取可回查的依據；不支援的部分結算或已結算認列變更保持拒絕。公開的是問題與控制原則，完整版本解析與 SQL 不公開。現行契約及實作定位已存在；各分支的執行結果仍依[指定版本](STATUS.md#verification)判讀。

**後續有界操作紀錄。** 9/29～30 的 `a455028` 合成演練接續完成清帳、同額摘要更正與關帳／重開。認列、清帳、沖回、重作共四筆分錄、11 行，各筆平衡；最後銀行借餘 210、應收 0、收入貸餘 200、銷項稅貸餘 10，並非四次銷貨。該輪也記錄 16 項操作／顯示／串接問題；後續有部分修復，不能改寫成最新 main 的整輪通過或真實公司月結驗收。

<a id="recovery"></a>
## 2. 網頁逾時，是沒入帳，還是已入帳但沒收到回覆？

**問題。** 使用者看到錯誤，不足以判斷資料庫沒有提交。直接換一個新操作再送，可能造成重複財務影響；直接顯示成功也會掩蓋未知狀態。

**系統的處理原則。** 保留原操作與內容、查回結果，區分已提交、仍處理中及需要專用查核的情形。能重試時沿用原操作身分；同一身分不能偷偷換內容。受控命令的提交紀錄與業務寫入相互綁定，舊執行不能完成另一個新嘗試。

```text
送出操作 → 回覆遺失 → 保留原操作 → 查明結果
                                      ↓
                  取回原結果，或依允許條件恢復
```

**可查看的成果。** 下方 `9012a79` 歷史瀏覽器案例包含實際提交後遺失回覆，再以相同內容與操作鍵重試；這是該次限定流程的紀錄，不是所有命令都具相同恢復能力。

**取捨。** 結果未明時先阻止新提交，操作上較保守，但不把網路錯誤當成新交易。外部服務、匯出或多交易工作可能要另查，不能用通用重試承諾「任何失敗都自動恢復」。

<a id="organization"></a>
## 3. 同一人服務多個客戶，切換組織後哪些資料必須失效？

**問題。** 在客戶甲有權限，不代表在客戶乙也有；即使切換後隱藏按鈕，舊請求仍可能稍後回來，把甲的資料重新填進乙的畫面。

**系統的處理原則。** 個人身分與各組織成員資格分開，每個組織有自己的角色及細分權限。切換須使用既有授權並輪替工作階段；前端清除舊資料、讓過期回應失效，後端與資料庫在操作時仍重新檢查。平台管理、一般組織管理與會計命令也是不同授權。

| 情況 | 判斷界線 |
| --- | --- |
| 在甲是管理員，到乙查資料 | 仍須具有乙的有效成員及對應讀取資格。 |
| 切換後收到舊查詢回覆 | 不應重新呈現已失效身分／組織的資料。 |
| 使用者看得到案件 | 不代表能核准、過帳或擴大資料範圍。 |
| 具名審查者下載或回覆 | 限原指派、期限與內容；回覆不建立正式外部結論。 |

**取捨。** 多處重驗增加狀態管理，但不把安全責任交給導覽列。最新文件已有跨組織雙分頁等驗收範圍紀錄；本次未取得該批庫外最終報告，不能宣稱上述全矩陣已在最新來源重跑。完整事務所團隊與委任管理仍未完成。

## 4. 測試通過後，真人操作仍發現什麼？

**兩個流程，不能互相代替。** 10/01～02 的 `e4258f2` 已有指定 PostgreSQL 範圍 51 檔／615 項成功紀錄，自動化瀏覽器的 105 元草稿補件為 210 元流程也通過。10/02 我親自操作時，卻將 105 元原發票配上 210 元更正認列證據，仍能完成確認、核准及過帳；AI 隨後唯讀核對保存結果，沒有改帳讓它看起來正確。

| 原件與結果 | 該合成案例的實際狀態 |
| --- | --- |
| 原發票 | 未稅 100、稅額 5、總額 105。 |
| 錯配的認列證據 | 未稅 200、稅額 10、總額 210，屬更正版本。 |
| 核准與過帳 | 確認及核准成立；最後仍以 105 過帳，借貸各 105。 |
| 修復狀態 | 反例及原件已保存；尚未完成最小根因定位、修復與回歸，不算成功案例。 |

**這改變了下一步的優先序。** 有來源、有 hash、有核准紀錄、借貸平衡，仍不足以證明不同證據的內容與版本相符。應先針對這個反例修復控制、加入負向驗證，而不是用更多測試數或文件補齊宣稱核心已完成。

我也回報未實際閱讀證據仍可核准。但當次有 HTTP 取件與 reviewed ID，沒有完整 checkbox 狀態紀錄，因此**不能推定已證實「未勾選也可繞過」**。技術讀取或聲明與人的理解、比對是否充分，是不同問題。摘要及交付說明接受單字元，也不能當成內容充分或真實交付的證明。

這九項本人操作不是九項全數 PASS；同一人切換合成帳號也不是三位獨立專業覆核者。完整系統的 Windows `fast` 及 Linux 全測尚未取得單次全綠，版本與計數限制見[驗證狀態](STATUS.md#verification)。

## 5. 我的需求、取捨與 AI 分工

一個有原紀錄的例子，是我要求改善來源重複抄錄、欄位錯誤干擾與覆核拒絕原因。調查發現其中一次拒絕是有效政策正確阻擋稅額矛盾，真正要修的是提早提示及解釋，**不是放寬會計規則讓操作通過**。我也選擇保留原錯誤案件作為證據，不把它改成成功。

| 分工 | 可檢查的內容 |
| --- | --- |
| 我提出問題與要求 | 減少重抄、保留文件原值與人工修正、拒絕須可定位、終態不能提示已失效的操作。 |
| 我決定範圍與取捨 | 保留原錯誤案件；不以新增 OCR、改原帳或解除必要控制解決本輪互動問題。 |
| 我實際執行的驗證 | 10/01～02 親自執行公開樣本、部分 PostgreSQL／fast 命令及結果核對，並完成九項介面操作，發現上述錯配反例。 |
| AI 協助實作及驗證 | 查核原因、修改程式、補測試、同步文件；本輪另協助環境除錯、部分後續自動化、唯讀核對及證據整理。 |
| 個人能力的界線 | 部分命令與真人操作由我完成，不代表全部實作、除錯或測試皆由我獨立完成，也不是第三方驗證。 |

以上分別由使用流程修復紀錄與 10/01～02 操作紀錄支持；我的需求判斷、親自驗證及 AI 協作分開陳述，不以測試數推定個人職級或整套系統正確。

## 7. 可自行檢查的政策程式

[公開模組](../src/domain/accounting/posting_policy.py)與[測試](../tests/test_posting_policy.py)保留原來源 `4841c001`。其中 101＋5＝106 的合成例子，可檢查來源欄位不足、科目語意不符、金額矛盾或政策自我核准時的拒絕。

模組使用 `Decimal`，不連線、不呼叫 AI、不寫入帳簿；它信任呼叫端提供的來源及核准欄位。`proposed`／`posting_allowed=True` 只是函式判定，不代替完整系統的來源、權限與過帳重驗。執行方式見[首頁](../README.md#執行公開模組測試)。
