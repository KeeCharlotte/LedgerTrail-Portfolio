## 1. 先定義「應該發生什麼」，再執行

本輪將風險整理為 **18 列財務聲明、20 列資訊一般／處理控制與 9 項分析程序**。這些是本專案的對照項目，不是準則條文總數、獨立測試總數或專業認證。16 項修復／契約調整也包含測試資料、工具及文件問題，不能寫成「16 個產品漏洞全部消失」。〔E01〕

### 測什麼？

| 問題 | 刻意安排的情境 | 不只看畫面，還看什麼？ |
| --- | --- | --- |
| 交易與證據是否相符？ | 同額但不同發票、同發票但金額不同、損壞或失效來源；另放合法對照組。 | 被拒絕的決策有沒有寫入、是否產生分錄；原始文件及歷史是否保留。 |
| 金額是否在驗證前失真？ | 超精度、微小負值、非有限值；另放零與等值尾零。 | 原值是否精確接受或拒絕；失敗後有沒有留下半套入件。 |
| 權限及獨立覆核是否成立？ | 製單者／覆核者自行過帳、跨組織、失效身分；另以適當第三個帳號操作。 | 服務層與資料庫都拒絕不合法寫入；換角色名稱不能取代換實際使用者。 |
| 重送、更正、關帳會不會改錯帳？ | 同請求重送、核准後條件變動、關帳期間更正、合法未收款應收。 | 分錄數、金額、原歷史、更正關聯及期間狀態，而非只有成功訊息。 |
| 報表是否漏列或沿用舊快取？ | 收款前後、更正前後、跨期追加與沖回、分類及損益結轉。 | 事前預期金額與實際彙總；區分正式受控命令和只供報表讀取的種子資料。 |
| 驗證結果是否可信？ | 漏列測試、模擬 API、掃描器未執行、不同部署入口、來源中途改變。 | 實際案例清單、原始 JUnit、退出碼、來源前後雜湊及結果的適用範圍。 |

### 怎麼做？

```text
固定來源與合成資料範圍
        ↓
事前列出風險、預期金額及應拒絕條件
        ↓
先在修復前版本重現錯誤，保存原始失敗
        ↓
分開測服務入口、真實資料庫及瀏覽器
        ↓
修改必要控制或過時測試，不降低正確的拒絕條件
        ↓
合法對照、負向反例及受影響回歸一起重跑
        ↓
逐案例核對結果、重複計數、來源及未執行範圍
        ↓
保留歷史失敗，另記修後結果與仍未成立的條件
```

資料庫套件各用新建的隔離 PostgreSQL，先正常部署、再重跑遷移，讀回實際權限與物件目錄後才測業務。涉及資料庫最終寫入的控制，另測直接 SQL 路徑，避免只證明 UI 或服務先擋住。每個原始結果保留前後來源、退出碼與 JUnit；失敗或被略過不能靠總數抹除。〔E01、E02〕

財務檢查使用精確金額、借貸差額 0、未授權寫入增量 0 等工程條件。這不是企業財報重大性，也不是從真實交易母體推估錯誤率。授權測試與本地自動化不構成獨立適格查核。〔E01〕

## 2. 兩個會計反例：不只測「應該成功」

### A. 105 元發票，不能用 210 元文件佐證

原人工案例的發票是未稅 100、稅額 5、總額 105；被選中的認列文件卻是 200、10、210。借貸各 105 仍然平衡，卻不能解決兩份資料內容互相矛盾。〔[10/02 原操作](CASE_STUDY.md#manual-counterexample)〕

**操作順序。** 準備原發票與固定模板文件，先讓錯配文件走認列確認的服務入口，再以真實資料庫直接呼叫受控寫入路徑。修前新反例原本預期拒絕，卻沒有出現拒絕；因此不是僅憑畫面推測問題。修後仍保留同一不合法輸入，再安排合法文件及合法補件作對照。〔E01、E03〕

| 實際測試 | 操作及事前預期 | 修後核對 |
| --- | --- | --- |
| 錯額 | 105 發票配 210 的已辨識模板，分別走服務與 SQL；應在決策寫入前拒絕。 | 不得留下成功認列，也不能因借貸可平衡而放行。 |
| 錯單 | 金額相同，但文件指向另一張發票；仍應拒絕。 | 不能只比總額而漏掉交易識別。 |
| 決策後重驗 | 在認列、核准及首次過帳的既有邊界核對當時有效文件。 | 後續寫入不能只相信先前狀態。 |
| 合法補件與對照 | 換成相符文件；銷貨、進貨、費用分別檢查既有合法路徑。 | 修復不能使所有文件一律被拒絕。 |
| 未辨識格式 | 使用不屬固定模板的文件。 | 留在既有受控人工判斷路徑，不聲稱機器已讀懂。 |

相應真 PostgreSQL 套件在 final08 為 **31/31 PASS，0 FAIL／ERROR／SKIP**，屬下方 675 個 PostgreSQL 案例的一部分，不另加總。控制只核對明確可辨識格式的原始內容與目前交易事實；不是通用 OCR，也不能證明文件記載的交易在現實發生。〔E03〕

**M02 與 M05 不混為一談。** 上述跟進了 M02 的固定模板內容錯配；M05 是「未實際點開兩份文件，只勾確認仍可核准」的人工覆核落差。內容檢查、下載紀錄或勾選都不證明人已閱讀、理解及正確比對；本輪沒有把 M05 宣稱為已解決。〔E01、10/02 原操作〕

### B. 先驗原始金額，不先捨入再驗

修前資料庫路徑會先將輸入轉成兩位小數，再檢查業務條件。部分小數差異或微小負值因此可能先被抹掉。測試改以原值為對象，驗有限性、範圍及能否精確表示，再准許儲存。〔E01〕

| 測試輸入／情境 | 實際操作 | 應有結果 |
| --- | --- | --- |
| `105`、`105.00`、`105.000`、`0` | 直接 SQL 及合法服務對照；等值尾零另查服務接受。 | 接受等值表示及合法零值，不擅自改金額事實。 |
| 超精度、微小負值 | 對入件兩個金額欄位分別／組合送入，另在補件送入 `105.001`、`-0.001`。 | 拒絕，不先捨入成合法值；失敗不得留下部分資料。 |
| `NaN`、正負無限值、空值 | 分別或同時送入適用金額欄位。 | 在正式寫入前拒絕；補件中的 `NaN` 同樣拒絕。 |
| 原值不同、捨入後相同 | 將本應相等的同幣金額改為不同原值。 | 精確比對原值，不能因轉換後相等而通過。 |
| 邊界 | 合法最大值與超出範圍值分開測。 | 合法邊界保留，越界拒絕，不縮小輸入來取得綠燈。 |

26 個永久金額正負向案例納入 **78/78 PASS** 的會計 PostgreSQL 套件；78 包含其他會計回歸，不能全數稱為新增金額測試。這同樣只是選定合成資料與契約範圍，不保證任意幣別及所有精度政策。〔E01、E04〕

## 3. 數字怎麼核對：先算預期，再查實際帳

### 16 筆合成交易，不只檢查「過帳成功」

先固定 16 張合成銷貨，每張未稅 101、稅額 5、總額 106，以及三個分工不同的合成使用者。事前預期是 **16 張發票、16 張傳票、16 筆唯一分錄、每筆 3 行，共 48 行；借貸各 16 × 106 = 1,696**。執行受控流程後，重新讀取該組織／該批次資料，逐張回勾入件、傳票與分錄，排除其他組織或無法回勾的額外資料，再重算筆數與總額。選定比較的差異為 0。〔E01、E07〕

| 另測的控制 | 操作 | 判斷依據 |
| --- | --- | --- |
| 製單／覆核者不得自行過帳 | 用衝突身分嘗試同一操作，再由適當第三人執行。 | 原測試斷言檢查拒絕與新增財務資料為 0；不同角色名稱不代替不同使用者。 |
| 同一請求重播 | 對既有請求再次操作。 | 原測試斷言核對同一分錄識別及不新增過帳；額外抽取則只觀察重播後的一筆分錄。 |
| 不只靠借貸相等 | 分別重算 16、48、每筆 106 與總額 1,696。 | 兩邊一起記錯也可能平衡，所以仍要對固定預期與關聯鏈。 |

**觀察限制不能省略。** N16 與單筆 soak 的額外抽取是重播後快照，沒有另行獨立取得重播前後差量。重播與拒絕的前後行為由原測試斷言支持；不能說額外觀察器也取得了那份前後證據。16 筆不是效能容量、真實客戶樣本或專業抽樣。〔E01〕

### 九項分析程序各測什麼？

下列均為 10/03 報告的已執行合成程序；預期在比對前指定，所列金額比較差異為 0。「報表專用種子」表示直接安排給查詢器的測試帳，不代表所有該類交易已有正常過帳入口。〔E01〕

| 程序 | 怎麼安排、比對什麼 | 預期數字／不變條件 |
| --- | --- | --- |
| 批次過帳 | 上述 16 筆逐張回勾並重算。 | 16 筆、48 行、借貸各 1,696。 |
| 單筆及重播 | 一筆 106 的受控交易、衝突身分拒絕及重播。 | 3 行、借貸各 106；同一分錄，不另生過帳。 |
| 賒銷後收款 | 正常受控賒銷 100＋5，再核准全額收款 105；比較前後彙總。 | 應收由 105 轉為 0、現金由 0 轉為 105；資產 105、負債 5、權益／獲利 100 不因收款重複增加。 |
| 分類與截止 | 報表專用種子含前期、本期及未來收入；逐項重算分類和期間。 | 本期獲利 32、含前期累積 72、資產 77、負債 5；未來收入 999 不納入。 |
| 損益結轉 | 報表專用種子分別安排獲利 100、虧損 25，再加入結轉資料。 | 未結轉損益歸零，但總權益仍為 100／−25；資產負債權益總量及原分錄不被改寫。 |
| 更正與舊快取 | 原賒銷 105 更正為 210；先測關帳拒絕、重開後執行，保留舊快取 105 再查詢及重播。 | 應收／資產 210、負債 10、權益 200；不能沿用 105，不能增加重播分錄或改掉原分錄。 |
| 跨期快取 | 報表專用追加／沖回資料，分別看原截止與本期總額。 | 原截止 105、後期增量 126、沖回後原截止 0、最終應收 231。 |
| 未收款與已結算 | 合法未收款應收與已確認銀行配對的全額結算分開測。 | 未收款應收 105 留著、銀行及結算筆數 0；另一已結算案例應收 0、現金 106。 |
| 關帳與期末覆核 | 空、未收款應收、未付款應付及已結算四種對照，明示期末調整不適用的覆核。 | 未收款 105、未付款 −100 不因關帳被清零；財務歷史及淨額變動 0，綁定正確組織與期間。 |

這些是有界金額／分類測試，不是一般財報生成能力或現金流量表驗收。部分 B4 原件使用 JSON 數值，後續十進位讀取不能恢復產生者可能已流失的精度；本次重算因此限定固定的小整數合成值，另與 SQL 文字彙總核對。純算術重算可增加交叉檢查，仍不是第二套獨立設計、具專業資格的會計演算法。〔E01〕

## 4. 驗證機制本身，也要測

### C. 對照清單，而不是看到測試檔就算覆蓋

將實際存在的 PostgreSQL 模組清單，與正式執行矩陣做集合比較。修前 51 套中只有 29 套列入矩陣，漏了 22 套；補齊後再加入本輪 2 套，成為 53 套。隨後逐套執行並核對非空 JUnit、零略過與相符來源，而非只修改配置就宣稱驗完。〔E01、E02〕

再逐一取出 fast 中 645 個被略過的案例識別，連參數一起比對真正執行的補證。675 個 PostgreSQL PASS 中，36 個已在 fast 通過，不再計一次；其餘 639，加 Linux 6，剛好覆蓋全部 645。另檢查多出、重複或缺漏節點；missing 為 0，原 fast SKIP 不改成 PASS。這是本地執行，不是 GitHub Actions 跑過。〔E02〕

### D. 瀏覽器測試：先分清真實後端與模擬

八支原腳本的導覽、提示、inline 文件預覽、必填檢查或唯讀欄位已與正式 UI 契約不同步。本輪先判斷正式行為是否正確，再修測試資料及操作；不為符合舊腳本而解除限制。〔E01、E05〕

| 測什麼 | 瀏覽器中的具體操作與觀察 |
| --- | --- |
| 退回、補件、過帳與交付 | 建立合成資料、查看欄位錯誤、退回並補正，再覆核／過帳；讀取來源差異與帳跡，核對下載結果。 |
| 更正、結算與期間 | 按提議、核准、執行、拒絕、撤回的各自路徑操作；對讀回的金額及狀態，不憑按鈕出現便推定可執行。 |
| 權限與來源選擇 | 切換組織／工作區、選擇明確試點及文件；無權限、失效或不符來源仍要停止。 |
| 未知結果與晚到回應 | 安排回應遺失及導覽競態；保存原請求識別，不能用新請求盲目重送；舊回應不得覆蓋新畫面。 |
| 版面及輸入 | 桌面／手機檢查欄位、inline 錯誤與唯讀值；明確 HTTP 拒絕不誤標成結果未知。 |

最終 **25 個唯一腳本通過**：15 個接真實資料庫的合成流程、2 個由服務提供 UI 但模擬 API 回應、8 個獨立模擬腳本。30 次呼叫含重複，不是 30 個唯一測試；25 也不能全稱為真實後端端到端。這些自動化不證明真人讀懂文件或完成專業驗收。〔E05〕

### E. 掃描器沒有跑完，不是「找到弱點」

以非管理員身分的工具環境執行相依弱點掃描。原本快取不可寫，掃描沒有完成；包裝層卻把空結果加非零退出判成發現弱點。先用回歸重現，再讓每次掃描取得獨立可寫暫存位置，離開時清除；不提高權限、不忽略真正弱點。〔E01、E07〕

驗證分三類：**正常完成且沒有弱點、正常完成且有弱點、掃描本身失敗**。另外測啟動例外、空／無效輸出與清理，最後在原本受限身分及相依版本下取得真實掃描結果。8 個新增回歸在修前失敗，修後通過；這不是「未來依賴永遠無弱點」的保證。〔E01〕

### 部署及封裝：測的是交付環境，不只工作目錄

兩種既有部署入口各從獨立新叢集開始：先部署並執行 78 項會計案例，再在已有資料的狀態重跑遷移，接著測失敗後恢復；每一階段讀回物件、權限及限定的八表歷史快照。兩入口的 fresh、帶資料重跑、失敗恢復三次等價比較均無差異。這不是任意歷史版本升級、所有表或正式災難復原保證。〔E06〕

Release 收集器另核對來源與封裝後執行、遷移、清潔檢查及必要證據；enterprise-local 收集器執行其限定本地檢查與上述 16 筆合成流程。收集器成功只證明它完成規定的收集及判定，**預期應拒絕的正式資格檢查仍保持非零退出**，不靠改退出碼讓一切變綠。〔E07、E08〕

## 6. 已完成的檢查，不取代尚未成立的條件

最終正式結果仍是 `artifact_contract_valid=true`、`local_engineering_readiness_passed=false`、`production_go_live_allowed=false`。不只是「差外部認證」：指定的互動會計工作區端到端範圍、正式環境觀測、還原演練、效能／安全審查及正式信任證據仍有未觀察或未成立項目。〔E08〕

還要保留三種差別：

- **實作限制**：未知文件的內容仍靠人工；銀行 CSV 雜湊相同不獨立證明呼叫端的解析列與原文相同。本輪沒有新增通用資料庫解析器、可信解析收據或解除凍結選配能力。
- **證據限制**：合成帳號不同，不證明是不同自然人或適格人員；雜湊不證明交易真實；部分分析只有重播後快照。報表專用種子、真實受控過帳及模擬 API 均分開標示。
- **外部與營運限制**：真實客戶、交易存在、權利義務、專業政策採信、外部交付及整段營運期間控制有效性，不由一次工程測試取得。沒有統計抽樣信心水準，也沒有專業查核意見。

負責人提出前序人工反例、決定檢查範圍及要求保留失敗；本輪工程測試、修復及證據整理由 AI／工具協作完成。不能把全部命令與程式說成本人獨力完成，也不能把多個 AI 相互檢查稱為獨立專業覆核。這份公開報告要展示的是**問題如何成為可測條件，以及結果能支持到哪裡**。〔E01、[本人分工](CASE_STUDY.md#contribution)〕
