### 尚未解決的反例與驗收限制

**優先缺口是來源內容一致性，不只是補齊上線文件。** 10/02 真人合成演練將 105 元原發票搭配 210 元更正認列證據，仍成功確認、核准並過帳為 105 元。來源、雜湊、核准紀錄與借貸平衡同時存在，卻未攔下版本／金額矛盾。此反例已保存，尚未完成根因定位、修復及回歸，詳見[案例](CASE_STUDY.md#manual-counterexample)。

另有三項不能略過：讀取／勾選／核准不證明真人確實比對內容；短文字被接受不等於摘要或交付依據充分；Windows 相容性與同來源完整發布驗收仍未完成。上述都是限制，不把錯誤改稱合理規則，也不以更多局部 PASS 結案。

下列 14 類保留部分程式、資料庫物件或歷史設計，均不列入近期可用功能。重新納入須有具體需求、責任、風險與驗證，不能因物件存在就計為成果。

| 網路與責任 | 基準比較網路、跨組織風險網路、AI 責任評分／仲裁 |

**另列：帳齡、現金流等選配財務操作。** 正式帳務至未結項的權威投影尚未建立，現為部分實作、所有環境停用；不能將空表當作零餘額，或將手插樣本測試當成完整投影已完成。這修正舊公開版「已實作的唯讀財務查詢」容易造成的誤解。

來源系統的一般登錄／自行填寫勾稽、財報重編模擬、公開錨定及部分密碼遷移寫入也仍拒絕。它們與現行受控會計更正、合成來源流程不是同一個入口。

## 4. 剩餘工作的完成條件

| 工作 | 還需要成立什麼？ |
| --- | --- |
| 先修復已保存的會計反例 | 對 105／210 錯配建立可重現的負向案例，定位最小原因，修復後取得適用的 API／UI／真實 PostgreSQL 證據；不只改提示或放寬 expected。 |
| 驗證與平台缺口 | 處理 Windows 測試／工具相容性，保留原失敗，再對凍結來源完成相稱回歸及完整發布收集；補跑不能冒充整批通過。 |
| 首個真實試用 | 具名使用者、合法資料、明確範圍與排除項、比較基準及責任人；不先承諾省時或降錯比例。 |
| 真實資料接入 | 選定來源，完成解析、收件保存與轉接；保留原件、差異及人工確認，不把候選升格成事實。 |
| 交付包與離線驗證銜接 | 對齊正規化、雜湊及集合證明規則，保存相符來源的實際驗證結果。 |
| 政策及正式信任 | 完成必要採信機制，取得具範圍、資格與有效性的外部材料；只填 JSON 或「已核准」不足。 |
| 當前部署與完整發布驗收 | 核對真正執行來源、正常遷移及同版本完整收集；正式維運另做監測、還原與風險驗收。 |

以上列出缺口，不將全部長期構想當成下一輪承諾，也不以文件更新解除任何原有控制。
